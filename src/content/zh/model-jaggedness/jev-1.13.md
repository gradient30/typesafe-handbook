# Jev 1.13 锯齿

> Jev 并不完美。下面是 `jev-1.13` 已知的锯齿边，其中不少会在后续版本修掉。

**适用于 `jev-1.13`。** 最近核对日期：2026-10-02。

`jev-1.13` 快、概率校准过，常识判断也不错，但并不完美。它最擅长 [System One](/concepts/system-one) 任务。需要多一层间接推理的任务可能吃力。它对字面意思很较真。需要数值精度的任务它也吃力。

| 1 | [照字面读](#照字面读) | 把确切条件写进 instructions，并为每个选项写清 criteria |
| 2 | [数学与数字](#数学与数字) | 算术留在代码里 |
| 3 | [日期与时间比较](#日期与时间比较) | 先抽出分量，再在代码里比较 |
| 4 | [间接推理](#间接推理) | 减少跳转，直接点名相关 state |

| 6 | [对抗性内容](#对抗性内容) | 把提示写精确，上线前测边界情况 |

## 照字面读

`jev-1.13` 回答的是你写下的问题，不是你心里想的那个。范围词、否定、隐含条件都会按字面读。问题按 instruction 里的措辞作答；人可能会读出意图，模型不会。

**改为：** 在 `instructions` 里写明确切条件。要具体。边界情况放进 criteria。看到错答案、开始解释「我其实是想说……」时，那段解释就是 instruction 缺的另一半。解释不可避免时，拆成两个字面问题，在代码里组合。

## 数学与数字

Jev 不是计算器。数学逻辑强烈建议放在代码里。语义问题它比数学问题做得好。

### 计数

`jev-1.13` 计数不可靠。这包括一个词里有几个字符、一段话里某词出现几次、长列表有几项。模型认的是答案的形状，不是在逐项清点，被数的东西越大，误差越大。

问计数问题之前，先问这个计数为什么需要模型。如果单位是正则或解析器能找到的，计数属于代码，模型加不上什么。

**改为：** 在代码里计数。要数符合某标准的项时，在代码里遍历候选，每一项问一个问题，再自己把答案加总。

```python
from typesafe_sdk import Noul, TypeSafeClient

client = TypeSafeClient(model="jev-1.13")
YES = 0.5  # up to you on what you want the threshold to be, depends on your usecase.

items = ["typesafe", "apple", "california", "banana", "likes", "calibration", "orange", "vertex"]

result = client.system_one(
    {"items": items},
    {
        f"item_{i}": Noul(instructions=f"Is `items[{i}]` the name of a fruit?")
        for i in range(len(items))
    },
)

count = sum(result.nouls[f"item_{i}"].noul > YES for i in range(len(items)))
```

### 数值表示

`jev-1.13` 对语义表示比对纯数字表现更好。例如用颜色英文名提问，会好过用十六进制。给它 RGB 三元组或 hex，它不能可靠判断两个值是否接近。

同样，高层编程语言的问题会好过底层汇编或二进制编码指令。

**改为：** 在代码里做换算，传入算好的数字或有名字的分桶。模型只留在真正是判断的那一段，例如一种颜色读起来算不算警告。

### 用 Score 做数学

不要用 Score 的输出（例如期望和概率）去计算两个等级之间某个数的精确幅度。可以用期望看它有没有过某个阈值，但 `jev-1.13` 的 Score 等级在数值校准上偏弱。靠在最近两个等级之间插值，还原不出精确数字。

## 日期与时间比较

`jev-1.13` 把日期当文本读，不当成有序的量。问两个日期哪个在前、相隔多远、是否落在某个窗口里，都不可靠。格式混用、相对指代，以及季度、结算窗口、应计区间这类领域边界，会更差。

**改为：** 把工作拆开。抽取是判断，交给模型。算术不是，留在代码里。

日期的每一部分都是小的封闭集合：十二个月、最多三十一天、有界的年份。于是抽取变成在枚举选项上的 [Choice](/primitives/choice)，而不是自由解析，也可以显式放一个「未写明」选项，缺的部分被报告而不是被猜。代码把各部分拼成真正的日期，并拥有之后的一切：排序、时长、偏移、星期几。

完整做法，包括相对日期和置信度门控，见 [日期抽取食谱](/cookbooks/date_extraction_cookbook)。

## 间接推理

带双重否定或复杂间接的 instructions，回答更不可靠。问「某属性的属性」，或需要多跳推理，都会掉准确率。

**改为：** instructions 尽量直接。能点名时，直接点出 state 里相关的部分。

## state 很大且充斥无关细节

state 里与决策无关的内容变多，准确率就下降。无关细节是干扰项，state 一大，也更难判断错答案来自输入的哪一段。

**改为：** 先在代码里检索和过滤，只送这个问题需要的字段。state 里滤不掉时，可以用 [Noul](/primitives/noul) 做相关性过滤。完整例子见 [RAG 段落分类食谱](/cookbooks/classifying_rag_passages)。

> **上下文长度有上限。** `jev-1.13` 的上下文窗口有界。具体 token 上限见 [模型](/models)。

## 对抗性内容

state 是数据，`jev-1.13` 默认不把它当成敌意输入。故意把模型往某个方向带的内容——注入的指令、刻意误导的框架，或替自己的分类辩护的文本——都可能推动答案。这一点预期以后会改进。

**改为：** criteria 写明确。面向大量用户之前，把集成测透。

## instructions 与 criteria 互相矛盾

`instructions` 和 `criteria` 要的不是同一件事时，`jev-1.13` 可能糊涂。措辞清楚时表现最好。例如一个 Noul 把 `true` 映射成否、`false` 映射成是，会更差。instruction 应当让普通人读得懂。

**改为：** 把 criteria 当成 instruction 的延伸。用清楚、精确的语言让二者对齐。

## Choice 选项顺序

有些情况下，[Choice](/primitives/choice) 选项的顺序会影响答案，`jev-1.13` 会偏向排在前面的选项。

**改为：** 重排选项，复查答案是否仍然一致。

## 生成

`jev-1.13` 不是为生成文本训练的。用一串 Choice 硬逼它生成，效果不好，也很慢。做数据抽取时，更好的做法是用正则或生成式模型先抽出候选，再让 `jev-1.13` 挑选正确的那一个。

**改为：** 答案空间有界时，把抽取做成选项上的 [Choice](/primitives/choice)，而不是直接要那个值。真的需要生成文本，用别的模型。

> **提醒，避免下面这些：**
>
> * 问模型去做代码能精确算出来的事。
> * 把好几个判断藏进一个问题。
> * System Two 任务：更多层间接。
> * 在 `state` 里给超过这个问题所需的上下文。Jev 会受 context rot 影响，无关材料会掉准确率。
