## 它怎么工作 {#how-it-works}

### 投机扇出 {#speculative-fan-out}

这里展示的主要模式是 [投机扇出](/patterns/fan-out)。每一条用户请求都对着一长串问题评估，包括许多对大多数请求最终都不相关的问题。

考虑下面这条用户请求：

> "Turn off all of the lights in the house"

这是一条很简单的请求，代码只需要考虑下面这些问题的答案：

* 「这是哪一类请求？」（智能家居指令）
* 「这条请求针对哪个范围？」（整栋房子）
* 「这条请求针对哪类设备？」（灯）
* 「灯上应该执行什么动作？」（关掉）

注意最后一个问题是在假定用户在对灯下指令的前提下写的，而我们在还不知道用户实际在请求什么之前就问了它。这就是所谓「投机性问题」——在还不知道它是否相关之前就问，从而并行评估所有问题，事后再靠代码滤掉无关结果。这是用同一组问题处理各种各样用户请求的关键模式。

#### 错误做法：串行 API 调用 {#the-wrong-way-sequential-api-calls}

错误做法是把问题拆到多次 API 调用里，等到确定需要答案才去问：

* 「这是哪一类请求？」（智能家居指令）

然后，只有在知道它是智能家居指令之后：

* 「这条请求针对哪个范围？」（整栋房子）
* 「这条请求针对哪类设备？」（灯）

然后，只有在知道它针对灯之后：

* 「灯上应该执行什么动作？」（关掉）

这种做法优化的是问题数量最少，但最终比一开始就把全部问题打进一次 API 调用更慢、更贵。

### TypeSafe 和 LLM 搭配 {#typesafe-and-llm-pairing}

这个演示也展示了 TypeSafe 如何和 LLM 搭配，处理有时需要字符串生成步骤的系统：

**拆开复合用户请求：** 这个演示里有一个 Noul 问题，用来识别用户请求是否在要求不止一个独立动作。如果为真，系统用 LLM 把请求拆成原子指令列表。拆开后的请求再分别由 TypeSafe 评估。

**回退到对话 LLM：** 当 TypeSafe 判断用户查询是在要一般信息或闲聊时，系统调用 LLM 生成自由形式的回复。这样，交互系统就能用又快又省的方式处理行为确定的请求，同时在需要时仍保留生成式 LLM 的灵活性。最初那次 TypeSafe 响应相对于 LLM 响应非常快，给整个系统增加的延迟可以忽略。
